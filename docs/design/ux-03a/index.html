ForeView / UX-03A #95 / design-only review

Keep the financial depth.
Make the workspace easier to read.

A current synthetic browser baseline, two visual directions, and concrete acceptance requirements. No application styles, workflows, financial calculations or private runtimes were changed.

Approved direction: A / Sage workspace. Selected by the maintainer on 21 October 2026: light sage navigation, warm surfaces, readable sans-serif type and rounded components, with optional compact financial tables. This approves the visual direction, not new financial functionality.

1. The two directions

A / Sage workspace

Light sage navigation, warm white surfaces, 16px cards, restrained shadows and more breathing room. Stronger separation between summary, supporting evidence and actions.

Selected by the maintainer. It follows the supplied warm/pastel direction and addresses the current visual density without imposing retirement as the product structure. Keep an optional compact table mode for data-heavy work.

Trade-off: less information above the fold. Large tables still need deliberate responsive treatment rather than smaller type.

B / Analyst workspace

Dark green navigation, cooler surfaces, 9px cards, flat borders and tighter row/section spacing. Retains stronger continuity with the current application.

Reference alternative, not selected. It preserves a clearer workspace boundary and fits more account data into the same viewport.

Trade-off: visually heavier navigation; less of a departure from the current utilitarian character.

Both alternatives use system sans-serif, tabular financial numbers, the existing ForeView name and its short slogan, explicit source/assumption badges, and 44px example form controls. There are no downloaded fonts, new libraries or connected save/projection actions.

2. What was actually inspected

Baseline: main commit 48a5871661d9413d0aa428d41c90a6a8c72c90c1, audited 21 October 2026 in local Playwright Chromium. Two disposable localhost runtimes were created: a generated synthetic household and an empty initialized database. Existing development/production servers and private documents were not used.

  • 45 current-app viewport captures: English/French at 1440 x 1000 and 390 x 844 for overview, assets, account editor, transactions, income, disabled tax-PDF import, expenses and employment projection; desktop administration/reference pages; validation, full help, synthetic RTL, loading/error fixtures and an empty-income state.
  • 16 static concept renders: both directions across five desktop views and three mobile views. Concept navigation and standard/compact table switching pass the dedicated renderer checks; no page-wide overflow was found at 390px in those three mobile concepts.
  • Financial invariance: dashboard, accounts and employment-projection API responses were identical before and after the current-app audit. Native validation prevented the unsaved draft from becoming a record.
  • Observed checks: file-required import controls disabled in all four locale/viewport combinations; invalid account form blocked; account and help Escape close passed; synthetic RTL direction was applied. No page JavaScript exceptions were captured.
  • Known limitations: the prototype is English-only and uses labels showing French-ready layout, not a translated prototype. Actual current-app en-CA/fr-CA evidence is captured separately. Synthetic RTL uses French fallback, not Arabic translation. Viewport captures do not prove every below-the-fold action, screen-reader behavior, browser or state is correct.

7. Selected direction and implementation boundaries

  1. Selected: A / Sage, including optional compact financial tables. B remains a reference alternative, not a second theme to implement.
  2. Navigation on mobile: the prototype screen-switcher is not the final application shell. UX-03C specifies and verifies its responsive disclosure/drawer behavior without losing module links.
  3. Typography/density: use the proposed readable 16/14/12px hierarchy and approximately 44px primary controls as implementation targets; validate long translations, zoom and compact tables instead of copying fixed pixels blindly.
  4. Approval boundary: visual/interaction direction only. Invented KPIs, historical chart APIs, changed routes, new retirement calculations and new legal documents are not authorized by this choice.

Maintainer selection: A / Sage, 21 October 2026. The selection is recorded in issue #95. Detailed implementation remains divided among the existing UX-03 children, with their own tests, review and merge approval.

8. Reproduction and verification

Install the repository's existing dev dependencies and Playwright Chromium. No new dependencies are required. Concept rendering works without any application server:

node docs/design/ux-03a/render-alternatives.mjs
node --check docs/design/ux-03a/capture.mjs
node --check docs/design/ux-03a/render-alternatives.mjs

Start the review-only launcher from the repository root. It always creates temporary runtimes, copies the locale catalogs, registers synthetic RTL, and binds two ephemeral localhost ports. It does not accept a private runtime path. Keep it running while capturing; interrupt it afterward to close both servers and clean its temporary data:

PYTHONPATH=. .venv/bin/python docs/design/ux-03a/serve.py

Supply the two printed URLs to the runner. It rejects ordinary application servers without the launcher's synthetic-audit marker, before changing any preference or capturing records:

node docs/design/ux-03a/capture.mjs http://127.0.0.1:SYNTHETIC_PORT http://127.0.0.1:EMPTY_PORT

The runner edits only the isolated language preference, opens/cancels forms, injects browser-only dashboard responses and validates factual-read-model invariance. It writes PNGs and measurements alongside this brief, or to an optional third output-directory argument. Browser exceptions fail the run on navigation and again before measurements are published. A regression test verifies that an exception cannot produce successful evidence. Native validation blocks the deliberately incomplete form. Generated baseline files can vary with system date and browser; they are review evidence, not byte-deterministic golden tests.

Use make qa for repository verification before publication. Dedicated render checks cover static prototype selectors, standard/compact switching, JavaScript errors and sampled mobile overflow; they do not establish complete application accessibility.
